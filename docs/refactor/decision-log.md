# Decision Log — Blitzy Sandbox Backstage Refactor

This document fulfills **Rule R3 (Explainability)** of the Agent Action Plan. Every non-trivial decision made during this refactor is captured below with rationale and risks. A decision is non-trivial if a competent engineer could reasonably have chosen differently. Deviations from a literal or obvious interpretation of the requirements appear here as explicit entries; unexplained deviations are treated as defects.

This file is **distinct** from the upstream Backstage ADRs in [`../architecture-decisions/`](../architecture-decisions/). The ADR format (numbered files with id / title / description front matter and Context / Decision / Consequences sections) is reserved for upstream governance records. This refactor decision log is a single flat Markdown table specific to this pull request.

For the requirement → file/test mapping, see [`traceability-matrix.md`](traceability-matrix.md). For the visual before/after diagrams, see [`architecture-before-after.md`](architecture-before-after.md). For onboarding guidance, see [`onboarding-addendum.md`](onboarding-addendum.md). For follow-on improvements, see [`next-tasks.md`](next-tasks.md).

---

## 0. How to Read This Document

Each decision below is a four-column row. Columns mean exactly:

- **Decision** — A single, concrete choice and the artifact it produces. Reads as "what we did".
- **Alternatives Considered** — Every option that was on the table at the moment of decision. Reads as "what we did not do, and why the choice was not obvious".
- **Rationale** — The principled reason the chosen alternative was selected. Links back to AAP sub-sections where applicable.
- **Risks** — The downside the decision carries and the mitigation that reduces residual risk to acceptable.

Reviewers cross-referencing the code should find a pointer to this decision log, not inline rationale comments. AAP §0.7.1.3 (R3 rule) states: _"Do not embed rationale in code comments. The decision log is the single source of truth for 'why' decisions."_

The decisions in Section 1 are sequenced from most-user-visible (catalog count, top-bar, audit middleware) to most-internal (policy packaging, logo mechanism, email source). This sequencing helps reviewers triage the highest-impact decisions first. Section 2 documents decisions that deviate from a literal interpretation of the user's requirements and therefore require explicit explanation per R3.

### 1.1 Notes on Section 1

- Row 1 is the bug fix the user explicitly diagnosed. Its rationale draws directly from the user's quoted observation: "the actual catalog items displayed are correct; only the count displayed at the top is wrong." (AAP §0.1.3)
- Row 2 sets the chrome substrate for every other UI/UX change. Without a layout-blueprint mount point, Settings / Support / Logo have nowhere to go after the sidebar is removed.
- Rows 3, 4, and 6 together implement AAP §0.5.1.3 (Workstream C — Authorization, Audit, and User Tracking). They are co-dependent: the policy (row 4) reads the email extracted by the resolver (row 6); the audit middleware (row 3) emits events that prove the policy decisions are tracked.
- Row 5 is the smallest decision but disproportionately consequential for accessibility — the alternative "Link with preventDefault" is a footgun that ships in many sites and degrades the experience for keyboard and screen-reader users.

### 2.1 Notes on Section 2

- Row 7 (feature flags) is a process decision more than a code decision; it constrains how this PR is shipped and rolled back. The decision is recorded here because a competent engineer could reasonably have preferred phased rollout.
- Row 8 (data-model preservation) is the most likely source of future confusion. The phrase "full removal" in the user's requirement is interpreted as "full removal of the user-facing surfaces", consistent with AAP §0.3.2's explicit out-of-scope boundary around the catalog backend persistence layer.
- Row 9 (per-entity TechDocs) clarifies a scoping ambiguity in the word "Documentation tab". The implicit prerequisite was already called out by the AAP authors in §0.1.1; this row makes the decision auditable.
