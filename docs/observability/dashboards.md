# Observability — Dashboards and Metrics

This document fulfills **Rule R1 (Observability)** of the Agent Action Plan: the Blitzy Sandbox Backstage portal ships with structured logging, distributed tracing, Prometheus metrics, health checks, and an importable Grafana dashboard. This page is the operator-facing reference for those signals and for how to import the companion dashboard template at [`dashboard-template.json`](dashboard-template.json).

For the WHY behind each metric naming and panel selection, see [`../refactor/decision-log.md`](../refactor/decision-log.md). For where these signals fit in the architecture, see [`../refactor/architecture-before-after.md`](../refactor/architecture-before-after.md). For the augmented GitHub sign-in resolver that emits `user-login`, see [`../auth/identity-resolver.md`](../auth/identity-resolver.md).

## 1. Overview

The Blitzy Sandbox Backstage portal exposes four observability pillars: structured logging (Winston-backed via `coreServices.logger`), distributed tracing (OpenTelemetry SDK with `getNodeAutoInstrumentations()`), Prometheus metrics (`/metrics` on port `9464` via the `PrometheusExporter`), and health/readiness checks (`/.backstage/health/v1/liveness` and `/.backstage/health/v1/readiness`, mounted by `coreServices.rootHealth` through `createHealthRouter` in `@backstage/backend-defaults`). Each pillar is wired in the backend composition root and is invoked by every plugin that accepts the standard `coreServices.*` dependency set.

- **Reused infrastructure** (already present in the source branch):
  - `coreServices.logger` — Winston-backed `LoggerService` injected via standard `deps` mechanism.
  - `packages/backend/src/instrumentation.js` — wires `NodeSDK` from `@opentelemetry/sdk-node`, registers `getNodeAutoInstrumentations()` from `@opentelemetry/auto-instrumentations-node`, and binds the `PrometheusExporter` from `@opentelemetry/exporter-prometheus`. This automatically emits HTTP, Express, fetch, runtime, and process metrics families (see §4.2).
  - `/.backstage/health/v1/liveness` and `/.backstage/health/v1/readiness` endpoints, mounted by `createHealthRouter` in `packages/backend-defaults/src/entrypoints/rootHttpRouter/createHealthRouter.ts` and exposed by `rootHttpRouterServiceFactory` on the backend's API port (`7007` by default).
  - `packages/backend/prometheus.yml` — example Prometheus scrape configuration.
- **Added by this refactor**:
  - Two new audit event IDs emitted via `coreServices.auditor`: `user-login` (from the augmented GitHub `signInResolver` in `packages/backend/src/authModuleGithubProvider.ts`) and `entity-access` (from the catalog access-audit middleware in `plugins/catalog-backend-module-access-audit/src/module.ts`).
  - Three custom Prometheus counters emitted via `@opentelemetry/api`: `user_login_total` (from the augmented GitHub `signInResolver`), `entity_access_total` (from the access-audit middleware), and `blitzy_permission_decisions_total` (from `BlitzyPermissionPolicy.handle()`). Each counter is defined in a per-plugin `metrics.ts` module that creates a named meter and exports a `Counter` instance plus a label-bucketing helper.
  - A Grafana 10.x dashboard template at [`dashboard-template.json`](dashboard-template.json). All panels — both the auto-instrumented panels (catalog query latency, HTTP error rate, Node.js heap usage, service health) and the custom-counter panels (audit events per minute, permission decisions) — render data immediately on import once the first sign-in, entity read, or permission check occurs.

To prove the entire stack works on your machine, follow the verification checklist in [Section 8](#8-local-verification).

## 2. Structured Logging

### 2.1 Logger source

The Backstage backend logger is `coreServices.logger`, a Winston-backed `LoggerService`. Plugins receive it via the standard `deps` mechanism in `createBackendModule`. In production environments it emits JSON log lines to stdout; in local development the same JSON is produced (use `jq` to pretty-print).

### 2.2 Log shape

Each log line follows a canonical JSON shape:

- `timestamp` — ISO 8601 UTC, e.g. `2025-05-22T00:32:14.123Z`.
- `level` — one of `error`, `warn`, `info`, `debug`.
- `service` — the plugin or module that emitted the log, e.g. `auth.githubProvider`, `catalog.accessAudit`.
- `correlationId` — a per-request correlation ID propagated via `httpAuth.credentials` memoization; uniquely identifies a single inbound HTTP request across all log lines and audit events it produced.
- `eventId` — present only on audit events; one of `user-login`, `entity-access` (see [Section 6](#6-audit-events)).
- `meta` — a free-form JSON object with event-specific metadata.

### 2.3 Correlation ID propagation

The `correlationId` is generated by Backstage's HTTP middleware on each incoming request and propagated through child contexts automatically. The `coreServices.auditor` service attaches it to every audit event without requiring explicit threading. To trace a request end-to-end across logs, audit events, and traces, filter on `correlationId` in your log aggregator.

### 2.4 Consuming logs

Three single-line patterns for the local shell:

- `yarn start 2>&1 | jq '.'` — pretty-print JSON logs locally.
- `yarn start 2>&1 | grep '"eventId":"user-login"'` — filter audit events for sign-ins.
- `yarn start 2>&1 | grep '"correlationId":"<id>"'` — trace a specific request by its ID.

## 3. Distributed Tracing

### 3.1 SDK wiring

`packages/backend/src/instrumentation.js` is executed via Node's `--require` flag on backend startup (see the backend `start` script). It instantiates `NodeSDK` from `@opentelemetry/sdk-node` with `getNodeAutoInstrumentations()` registered. This auto-instruments HTTP servers and clients, Express middleware, `fetch`, the `pg` (Postgres) driver, DNS lookups, file-system calls, and roughly thirty other built-in and third-party library spans.

### 3.2 Versions in use

The OpenTelemetry packages pinned in `packages/backend/package.json`:

- `@opentelemetry/sdk-node` — `^0.211.0`
- `@opentelemetry/auto-instrumentations-node` — `^0.67.0`
- `@opentelemetry/exporter-prometheus` — `^0.211.0`

### 3.3 Configuring an OTLP exporter (Jaeger / Tempo / Honeycomb)

The source branch wires only the Prometheus _metric_ exporter and does **not** export traces by default — the `traceExporter` option in `instrumentation.js` is intentionally left commented. To export traces to an OTLP collector, set the following environment variables before `yarn start-backend`:

- `OTEL_EXPORTER_OTLP_ENDPOINT` — the OTLP gRPC or HTTP endpoint (e.g. `http://localhost:4317`).
- `OTEL_SERVICE_NAME` — the service name to attach to spans (e.g. `blitzy-backstage-backend`).
- `OTEL_TRACES_EXPORTER` — set to `otlp` to enable the OTLP trace exporter.

A future iteration may add an explicit `traceExporter: new OTLPTraceExporter(...)` to `instrumentation.js`; this is captured as a follow-up in [`../refactor/next-tasks.md`](../refactor/next-tasks.md) (entry 4, "Expand the audit dashboard with per-user breakdowns") by association.

### 3.4 Inspecting traces locally

To exercise tracing on a developer machine:

- Run a Jaeger all-in-one container: `docker run -p 16686:16686 -p 4317:4317 jaegertracing/all-in-one:latest`.
- Export `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317` and `OTEL_TRACES_EXPORTER=otlp`.
- Start the backend with `yarn start-backend`.
- Open `http://localhost:16686/` in a browser and select the `blitzy-backstage-backend` service to view spans.

## 4. Prometheus Metrics

### 4.1 Metrics endpoint

The Backstage backend exposes Prometheus metrics on `http://localhost:9464/metrics` via the `PrometheusExporter` from `@opentelemetry/exporter-prometheus`, wired in `packages/backend/src/instrumentation.js`. The scrape configuration template lives at `packages/backend/prometheus.yml` (default scrape interval `15s`, default target `host.docker.internal:9464`).

### 4.2 Auto-instrumented metrics

Out of the box, `@opentelemetry/auto-instrumentations-node` exposes the following metric families:

- `http_server_request_duration_seconds` — histogram; per-route HTTP request latency.
- `http_server_requests_total` — counter; per-route HTTP request count.
- `process_resident_memory_bytes` — gauge; Node.js process resident memory.
- `process_cpu_seconds_total` — counter; cumulative CPU time consumed by the process.
- `nodejs_eventloop_lag_seconds` — gauge; current Node.js event loop lag.

### 4.3 Custom counters (implemented)

The refactor ships three custom counters defined via `@opentelemetry/api` in per-plugin `metrics.ts` modules. The canonical metric names, label sets, and label-value vocabularies are documented here so the policy / auth / access-audit modules, the Grafana dashboard, and operator runbooks converge on a single contract. Each counter is emitted by its respective runtime module and is exercised by dedicated jest unit tests (`jest.spyOn(counter, 'add')`).

| Metric name                         | Type    | Labels                           | Emission site                                                                                                                                                                                  | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------- | ------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `blitzy_permission_decisions_total` | Counter | `{result, email_domain, action}` | `BlitzyPermissionPolicy.handle()` at `plugins/permission-backend-module-blitzy-policy/src/policy.ts`; counter declaration in `plugins/permission-backend-module-blitzy-policy/src/metrics.ts`. | Incremented exactly once per `PermissionPolicy.handle()` call. `result` is `ALLOW` or `DENY`. `email_domain` is bucketed by `bucketEmailDomain()` into one of `blitzy.com`, `other`, or `guest`. `action` is the permission attribute action (e.g. `read`, `create`, `update`, `delete`, or `unknown` when the permission has no attribute).                                                                                                                                  |
| `user_login_total`                  | Counter | `{provider, email_domain}`       | Augmented `signInResolver` in `packages/backend/src/authModuleGithubProvider.ts`; counter declaration in `packages/backend/src/metrics.ts`.                                                    | Incremented exactly once per resolver invocation that passes username validation, recorded before `auditor.createEvent` so the metric is not skipped if the auditor itself fails. `provider` is `github` today and is declared explicitly to stay forward-compatible. `email_domain` is bucketed by `bucketSignInEmailDomain()` into one of `blitzy.com`, `other`, or `unknown` (the last bucket covers both empty domains and the synthetic `@unknown.invalid` placeholder). |
| `entity_access_total`               | Counter | `{action}`                       | Access-audit middleware in `plugins/catalog-backend-module-access-audit/src/module.ts`; counter declaration in `plugins/catalog-backend-module-access-audit/src/metrics.ts`.                   | Incremented exactly once per audited entity read inside the response finalize callback, before `auditor.createEvent`, so the counter records every observed read regardless of whether the auditor itself fails or whether `finish`+`close` both fire. `action` is `read` today; write events would emit a separate `entity-write` counter per [`../refactor/next-tasks.md`](../refactor/next-tasks.md) entry 5.                                                              |

The `blitzy_` prefix on the permission counter distinguishes Blitzy-specific business metrics from generic Backstage / Node.js telemetry. The other two counters follow the OpenMetrics convention for cross-cutting business counters and are intentionally unprefixed.

### 4.4 Querying metrics

Three reference PromQL queries:

- `rate(blitzy_permission_decisions_total{result="DENY"}[5m])` — DENY decisions per second over a 5-minute window.
- `sum by (email_domain) (rate(user_login_total[5m]))` — sign-ins per second grouped by email domain.
- `sum by (action) (rate(entity_access_total[5m]))` — entity reads per second grouped by action.
- `histogram_quantile(0.95, rate(http_server_request_duration_seconds_bucket[5m]))` — p95 HTTP request latency (auto-instrumented by `@opentelemetry/auto-instrumentations-node`).
- `rate(http_server_requests_total{status_code=~"5.."}[5m])` — server-error rate per second (auto-instrumented).
- `process_resident_memory_bytes` — Node.js process RSS in bytes (auto-instrumented).

### 4.5 Cardinality discipline

Prometheus label cardinality is deliberately constrained. `email_domain` is a coarse bucket (the domain portion after `@`), never the full email address. `entityRef` is **never** a Prometheus label — it appears only in the `meta` field of the corresponding audit log line, where unbounded distinct values do not poison the metrics database. Per-user dashboards (which would require user-cardinality labels) are out of scope for this refactor and tracked in [`../refactor/next-tasks.md`](../refactor/next-tasks.md) entry 4.

## 5. Health Checks

The Backstage backend ships with liveness and readiness endpoints from `coreServices.rootHealth`, mounted by `createHealthRouter` inside `@backstage/backend-defaults`. Both bind to the backend API port (`7007` by default in this repo) rather than the metrics port. The endpoint paths are namespaced under `/.backstage/health/v1/` and are the only authoritative paths exposed by Backstage 1.48.0 — there is no top-level `/health` or `/readiness` route.

### 5.1 Endpoints

- `GET /.backstage/health/v1/liveness` — returns `200 OK` with body `{ "status": "ok" }` when the process is alive. Use this for liveness probes. Source: `createHealthRouter` in `packages/backend-defaults/src/entrypoints/rootHttpRouter/createHealthRouter.ts`.
- `GET /.backstage/health/v1/readiness` — returns `200 OK` with body `{ "status": "ok" }` once all registered root-scope services have initialized; returns `503 Service Unavailable` during startup. Use this for readiness probes. Source: same `createHealthRouter`.

### 5.2 Platform integrations

Fly.io, Railway, and Kubernetes all consume these via their respective `liveness_probe` / `readiness_probe` configuration blocks. The backend's port for these endpoints is the same as the API port (`7007` by default). When deploying behind an ingress controller, ensure the probe paths are not rewritten or gated by authentication.

### 5.3 Alias support

Backstage 1.48.0 does **not** expose a `/.well-known/healthcheck` alias or top-level `/health` / `/readiness` aliases by default. Operators who need shorter probe paths can mount a thin alias layer in `packages/backend/src/index.ts` via `coreServices.rootHttpRouter.use(...)`, but no alias is wired in this repo and runbooks must use the canonical `/.backstage/health/v1/*` paths.

## 6. Audit Events

Audit events are emitted through Backstage's `AuditorService` (`coreServices.auditor`) and land in the structured JSON log stream alongside ordinary log lines. They are distinguished by the presence of an `eventId` field — every other log shape rule from [Section 2](#2-structured-logging) applies unchanged.

### 6.1 Event types

The refactor introduces two event types:

- **`user-login`** (severity `medium`) — emitted on every sign-in (successful or failed). Meta fields: `provider` (`github` or `guest`), `username`, `emailDomain`, `userEntityRef`, `correlationId`. Source: `packages/backend/src/authModuleGithubProvider.ts`'s augmented `signInResolver`. The `correlationId` is a synthetic UUID generated inside the resolver because Backstage's `SignInResolver` callback signature does not expose the inbound Express `request` object — see §6.3.
- **`entity-access`** (severity `low`) — emitted on every user-credentialed entity read. Meta fields: `entityRef`, `principal`, `action` (`read`). Source: `plugins/catalog-backend-module-access-audit/src/module.ts`. Because this code runs as an Express middleware, it passes the inbound `request` object directly to `AuditorService.createEvent({ request, ... })`, so the correlation id is the canonical request-scoped correlation id rather than a synthetic UUID.

### 6.2 Lifecycle and severity

Audit events follow the `AuditorService.createEvent({ eventId, severityLevel, request?, meta }).success({ meta }) / .fail({ error, meta })` lifecycle. Each event is opened via `createEvent`, then either succeeded or failed exactly once. Severity is one of `low`, `medium`, `high`, `critical` and reflects the operational urgency of inspecting the event, not the underlying user impact.

### 6.3 Correlation

Correlation behavior differs by event type:

- **`entity-access`** events carry the inbound HTTP request's correlation id because the middleware has access to the Express `request` and passes it to `AuditorService.createEvent({ request, ... })`. Joining these audit events to ordinary HTTP log lines and to OpenTelemetry trace spans is a single-key filter operation on the canonical correlation id.
- **`user-login`** events carry a synthetic correlation id minted by the resolver (via `randomUUID()`) and stored in the audit `meta.correlationId` field. The Backstage `SignInResolver` callback signature is `(info, ctx) => Promise<BackstageSignInResult>` and does not expose the Express `request`, so the resolver cannot read the canonical HTTP correlation id. Operators correlating sign-in audit events back to HTTP requests should match on the surrounding request log lines (same `requestId` field) emitted by `coreServices.httpRouter` rather than expecting the synthetic id to match the HTTP correlation id.

### 6.4 Privacy posture

The audit `meta` block **never** contains the full email address, OAuth access tokens, OAuth refresh tokens, or the raw OAuth provider result payload. Only the domain bucket (`emailDomain`) and entity references are recorded. This is a hard security invariant enforced by unit tests in `packages/backend/src/authModuleGithubProvider.test.ts`. The reasoning is documented in [`../refactor/decision-log.md`](../refactor/decision-log.md) entry 6 ("Email source priority for domain check").

## 7. Grafana Dashboard Import

The companion file [`dashboard-template.json`](dashboard-template.json) is a Grafana 10.x-compatible dashboard JSON, ready for import.

### 7.1 Steps

1. Open Grafana in your browser.
2. Navigate to **Dashboards → New → Import**.
3. Upload `docs/observability/dashboard-template.json` from this repository (or paste its contents into the JSON text box).
4. When prompted, select the Prometheus data source configured to scrape the Blitzy Sandbox backend at `http://localhost:9464/metrics` (or the equivalent target in your environment).
5. Click **Import**.
6. Verify panels render data within roughly thirty seconds. Auto-instrumented metrics populate immediately; the custom counters populate only after the first sign-in / entity access.

### 7.2 Panel inventory

The template ships six panels. All panels render data as soon as the corresponding counters or auto-instrumented metrics have at least one observation:

- **Audit Events Per Minute** — `rate(user_login_total[1m])` and `rate(entity_access_total[1m])` stacked. Populated by the per-plugin custom counters described in §4.3.
- **Permission Decisions (ALLOW / DENY)** — `sum by (result, email_domain) (rate(blitzy_permission_decisions_total[5m]))`. Populated by the counter emitted from `BlitzyPermissionPolicy.handle()` described in §4.3.
- **Catalog Query Latency (p50 / p95 / p99)** — three series with `histogram_quantile(0.5|0.95|0.99, rate(http_server_request_duration_seconds_bucket{route=~".*catalog.*"}[5m]))` (auto-instrumented).
- **HTTP Error Rate** — `sum(rate(http_server_requests_total{status_code=~"5.."}[5m])) / sum(rate(http_server_requests_total[5m]))` (auto-instrumented).
- **Node.js Heap Usage** — `process_resident_memory_bytes` (auto-instrumented).
- **Service Health** — single-stat panel showing `up{job="blitzy-backstage"}` (Prometheus scrape liveness).

### 7.3 Customizing the template

The template uses generic Prometheus data source references. Adjust the `datasource` field in each panel if your Grafana environment uses a non-default data source UID. The Service Health panel assumes the Prometheus scrape job is labelled `blitzy-backstage`; the example `packages/backend/prometheus.yml` uses `job_name: 'prometheus'`, so operators deploying the dashboard will typically rename the scrape job (or change the query) to align labels.

## 8. Local Verification

The R1 rule states: "If you cannot exercise it locally, it is not delivered." This section is the canonical checklist for proving the observability stack works on a clean developer machine. Each step is a single concrete command with a deterministic expected outcome.

### 8.1 Step-by-step checklist

1. **Start the backend**: `yarn start` (frontend + backend together) or `yarn start-backend` (backend only). Wait until the console prints `Listening on :7007`.
2. **Confirm the metrics endpoint**: `curl -s http://localhost:9464/metrics | head -30` — should print Prometheus text format including `# HELP` and `# TYPE` lines for the auto-instrumented metrics.
3. **Confirm auto-instrumented metrics are emitting** (these are available at this checkpoint):
   - `curl -s http://localhost:9464/metrics | grep '^http_server_request_duration_seconds'` — HTTP request latency histogram (emitted by `@opentelemetry/auto-instrumentations-node`).
   - `curl -s http://localhost:9464/metrics | grep '^process_resident_memory_bytes'` — Node.js process RSS (emitted by the Node runtime instrumentation).
   - `curl -s http://localhost:9464/metrics | grep '^nodejs_heap_size_used_bytes'` — Node.js V8 heap usage (emitted by the Node runtime instrumentation).
4. **Confirm the canonical health endpoints**:
   - `curl -i http://localhost:7007/.backstage/health/v1/liveness` — should return `200 OK` with body `{"status":"ok"}`.
   - `curl -i http://localhost:7007/.backstage/health/v1/readiness` — should return `200 OK` with body `{"status":"ok"}` once initialization completes (it returns `503 Service Unavailable` during startup).
5. **Exercise sign-in and entity view to produce audit events**: open `http://localhost:3000/` in a browser, sign in via GitHub (or Guest), and click any catalog entity.
6. **Tail the structured audit log**: `yarn start 2>&1 | grep '"eventId"'` — should print at least one `user-login` event and at least one `entity-access` event from step 5.
7. **Confirm the custom counters are emitting**: `curl -s http://localhost:9464/metrics | grep -E '^(blitzy_permission_decisions_total|user_login_total|entity_access_total)'` — should print at least one line per counter after step 5 has produced a sign-in, an entity read, and a permission check.

### 8.2 Troubleshooting

- **`/metrics` returns 404 or connection refused** — confirm `packages/backend/src/instrumentation.js` is loaded via `--require` on backend startup; check `node --version` is `22` or `24` (the `engines.node` field permits `22 || 24`).
- **Permission decisions appear absent** — confirm `permission.enabled: true` is set in `app-config.yaml` so the policy is actually invoked; confirm the new plugin modules are registered in `packages/backend/src/index.ts`. If `blitzy_permission_decisions_total` is missing, hit a protected route to trigger at least one `handle()` call.
- **`/.backstage/health/v1/readiness` returns 503** — wait for backend initialization to complete (typically ten to thirty seconds on first start); inspect stdout for unresolved service initialization errors.
- **No audit lines in stdout** — confirm `coreServices.auditor` is in the plugin's `deps` block; the default `WinstonRootAuditorService` writes events through the same Winston logger used for normal log lines.
- **Custom counters missing from `/metrics`** — counters are lazy-registered on first observation. Exercise the relevant code path at least once (sign in, view a catalog entity, hit a protected route) before re-running `curl -s http://localhost:9464/metrics`.
